      # Dialog-tree markup survey for Kildeverket 0.2

      ## 1. Ink (Inkle)

      ```ink
      * {door_open} [Go through the door] -> corridor
      + Wait here.
          - (hub) You look around.
          * * "Who are you?"[] she asked.
          * ->
      - -> DONE
      ~ knows_name = true
      {seen_once|seen twice|seen again}
      ```
      (Per WritingWithInk.md: `*` once-only, `+` sticky, `{condition}` guards, `-` gathers, `(label)` labels double as read counts, `* ->` fallback, `{a|b|c}` sequences, `{&…}` cycles, `{!…}` once-only text, `~` logic lines, `TODO:` printed at compile, undefined diverts = warning + "loose end" runtime error.)

      Better than 0.2's draft:
      - Read counts are free: any knot/stitch/label address is itself an integer expression (`hub > 2`) — no separate `asked.*` namespace.
      - `TURNS_SINCE(-> knot)` and `CHOICE_COUNT()` give recency/pressure tests — 0.2 has `day >= N` but no "how long since".
      - Tunnels (`-> subroutine ->`) run a shared fragment and return — reusable interview beats.

      To steal: the full variation family (`{&…}` cycle, `{!…}` once-then-silent, `{~…}` shuffle — once-then-silent fits repeated document reads); address-as-count (every `(label)` is an integer term, `asked.frist >= 2` and bare `frist` both parse); tunnels as a "shared beat" primitive (rights info, samtykke).

      To avoid: implicit gather scoping — if 0.2 keeps `- (hub)`, REQUIRE the label; ink's fatal loose-end runtime errors — 0.2's "stubs, never fatal" is strictly better.

      ## 2. Yarn Spinner

      ```yarn
      => Guard: Greetings, citizen.
      => Guard: Hail, adventurer! <<if $player_is_adventurer>>
      => Guard: I used to be an adventurer like you... <<once if $player_is_adventurer>>
      ```
      Options are `->` lines with indented bodies and nesting; effects `<<set $x to y>>`; game effects `<<command args>>`; every line carries a `#line:` id for localization; the compiler auto-adds `#lastline` before option sets.

      Better than 0.2's draft:
      - `once` is an orthogonal MODIFIER, not a sigil: `<<once if $a>>` composes with any condition. 0.2's `*` vs `+` cannot express "sticky but only while stage 2".
      - Node groups + saliency: several nodes share a title, each with a `when:` header; engine picks the highest-complexity passing node (complexity is spelled out: `when: always` = 0, `when: $a` = 1, `when: once if $a or $b` = 3), tie-broken least-recently-viewed. A declarative dispatch mechanism — exactly the shape a card-keyed ask needs.
      - Stable `#line:` ids make Bokmål/Nynorsk/English extraction mechanical.

      To steal: `once` as modifier on choices, lines, and effects (keep `*`/`+` as sugar); node groups with a documented complexity rule; auto-assigned stable line ids written back into the file.

      To avoid: `<<…>>` for both flow control and game commands (parser cannot tell compiler-known from game-known — keep 0.2's closed `~ verb` list); least-recently-viewed tiebreak (nondeterministic-feeling — use declaration order).

      ## 3. Twine / Harlowe

      ```harlowe
      [[Link text->Passage Name]]
      (if: visits is 1)[First time here.]
      (set: $sak to "innvilget")
      (cond: $stage > 2, "text1", "default")
      ```
      `visits` is a per-passage visit-count keyword; `(visited:)`/`(history:)` query the trail; hooks `[…]` are the reveal/replace unit.

      Better than 0.2's draft: bare `visits` keyword (no naming ceremony for "have I been here before"); `(history:)` gives ORDERED trail access — "did the client mention X before I read the doc" — counts cannot express ordering; hooks rewrite a line in place.

      To steal: a bare self-count term (`besøk`) inside a block; an ordering predicate `before(a, b)` in the condition grammar.

      To avoid: the macro-soup (conditions, effects, and markup look identical — 0.2's `{…}` vs `~ …` vs prose separation is an asset); passage-per-beat fragmentation (opposite of one file = one case).

      ## 4. Twine / SugarCube

      ```sugarcube
      [[Go buy milk|Grocery][$bought to "milk"; $money -= 5]]
      <<if $condition>>content<<elseif $other>>alternate<</if>>
      <<set _temp to $name + 1>>
      ```
      `visited()`, `hasVisited()`, `lastVisited()`; `_temp` variables live one turn, unsaved; `<<widget>>` defines reusable macros.

      Better than 0.2's draft: SETTER LINKS — effects attached to the edge, evaluated on click, one line covers choice text + target + consequences; temp variables (scratch values that never enter the save); `<<widget>>` names recurring effect bundles.

      To steal: inline effect list on a divert (`-> target { ~ pay frist; ~ clock +1 }`); a named-macro declaration in the spine (directly the unlock-recipe primitive); turn-scoped temporaries.

      To avoid: open expression language (`<<run>>`, arbitrary TwineScript) — no static validation, no linting; keep 0.2's grammar closed.

      ## 5. Drafft

      Node-graph editor, not a text format. Ten node types (incl. Condition, Switch, Event, Note, Return); `@set` directives attached to OUTPUT PORTS run when that port is followed; export is structured JSON/HJSON/TOML/YAML.

      Better than 0.2's draft: effects on the edge (same insight as SugarCube, from the graph side — "which transition caused this state change" is structurally explicit); Switch nodes (one expression, N case ports — first-class N-way dispatch); Note nodes are first-class and survive round-trip.

      To steal: define WHEN a `~` line fires — Drafft's answer (on traversal, not display) is the right default; a `switch` construct keyed on a single term (e.g. the played card id); structured machine-checkable TODO/Note rather than free comments.

      To avoid: graph-first authoring — no canonical text source, no diffs, no grep, no merge. Generate the graph, never author in it. No localization/validation story — do not inherit that gap.

      ## 6. Chat Mapper

      Every node carries a Conditions field and a Script field, both Lua (`Variable["name"]`, `Item["name"]`). Visit state per entry via `Dialog[…].SimStatus`. Nodes have a GROUP and a PRIORITY — priorities compare only within a group. The F5 simulator shows every candidate red/green with condition status, priority, id, group. Localization = language-suffixed fields.

      Better than 0.2's draft:
      - Group + priority selection: among passing links, highest priority within the group wins. Cleanest published model for "which of many candidate asks fires".
      - Menu Text vs Dialogue Text split: what the player clicks ≠ what the character says. Casework needs short card-label vs full spoken ask.
      - The red/green condition simulator is the single best debugging affordance surveyed — shows WHY an option was hidden.

      To steal: two-field choices (menu text / spoken line); group + priority for card-keyed asks with the generic soft-reject at priority 0 in the same group; a "why hidden" trace reporting the failing sub-term of every suppressed choice (possible precisely because 0.2's grammar is closed).

      To avoid: Lua-in-a-field (unbounded expressions, mangled identifiers, errors only at simulation); arbitrary structural prohibitions (no-links-to-START) — 0.2's stub-anything policy is better.

      ## Cross-tool synthesis

      ### (1) Constructs multiple tools agree on that 0.2 lacks

      1. **`once` as a composable modifier, not a sigil** (Yarn, ink `{!…}`, Harlowe `visits is 1`). `*`/`+` cannot say "sticky until stage 3" or "effect fires once, line stays sticky".
      2. **Effects bound to the transition, not the node** (SugarCube setter links, Drafft `@set` on ports — evolved independently). Define effects-on-traversal; allow an inline effect list on a choice/divert.
      3. **Declarative candidate selection with an explicit tiebreak** (Yarn node groups + complexity, Chat Mapper group + priority, Yarn line groups). Three of six tools have a dispatch-table construct; 0.2 has only guarded choices, forcing hand-ordered mutually-exclusive guards.
      4. **Read/visit counts as first-class bare terms** (ink addresses, Harlowe `visits`, SugarCube `visited()`, Chat Mapper SimStatus). `asked.<label>` is on the right track — add a bare self-count keyword and ideally an ordering predicate.
      5. **Stable per-line localization ids, auto-assigned** (Yarn `#line:`, Chat Mapper suffixed fields). Retrofitting is expensive — auto-assign, write back, never renumber.
      6. **Distinct short label vs full text on a choice** (Chat Mapper Menu/Dialogue Text; ink `[bracketed]`). One character of syntax.

      ### (2) The three uncovered sections

      **Card-keyed call exchanges** → Yarn node groups / Chat Mapper group+priority, plus Drafft switch. Proposed: a `switch on card` block, branches keyed by card id, optionally further guarded, falling through to a `card:*` generic branch. Adopt Yarn's published complexity rule but replace the tiebreak with declaration order. The unmatched card is not an error — it is the `card:*` branch (stub philosophy applied to selection).

      ```
      exchange husleie
        ~ when card:leiekontrakt and not asked.frist   -> ask_kontrakt_tidlig
        ~ when card:leiekontrakt                       -> ask_kontrakt
        ~ when card:*                                  -> ask_generisk
      ```

      **Proposal pairs** → no surveyed tool has a native multi-key trigger; genuinely 0.2's own construct. Nearest: group+priority (specific pair beats generic) + named bundles. Recommendation: declarative `proposal` table, UNORDERED pair keys (canonicalise by sorting ids at parse), reuse `n of (a,b,c)`, and a linter-REQUIRED `otherwise` soft-reject row — the one place 0.2 should be strict, because a missing soft-reject is silence in the player's face.

      ```
      proposal hyp.samboer
        pair (folkeregister, kontoutskrift)  -> aksept
        pair (folkeregister, *)              -> mykt_avslag "Dette peker et sted, men ikke dit."
        otherwise                            -> mykt_avslag_generisk
      ```

      **Unlock recipes** → steal SugarCube's named-macro idea: a recipe is a named bundle of conditions + effects declared once, referenced anywhere. Same closed condition grammar in `requires`, same `~` verbs in `grants` — no new semantics, only a binding form. Gives the linter a reachability graph for free (orphans = warnings, never errors).

      **Cross-cutting recommendation:** Chat Mapper's red/green simulator is the highest-leverage tooling idea surveyed, and 0.2 can beat it: with a closed grammar, report WHICH sub-term failed for every suppressed choice/branch/pair/recipe. Ship that trace view before any graph view — and generate the graph from the file, never the reverse (the Drafft lesson).
