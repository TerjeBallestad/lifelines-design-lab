      RESOLVED (grill with Terje, 2026-08-06). Four rulings:

      1. Authoring model: hybrid (b). Two surfaces, one store — the script surface is where authoring starts (write the document, facts lift out), the canvas is where you wire and navigate. Two lenses on the same markup, jump-to-block both ways. Neither surface is primary — each owns the gestures it is best at. DD-003 amended and retitled accordingly.

      2. Node birth: both surfaces create, each with its native gesture. Script creates by naming (an unknown id in Supports/Opens/a weave jump becomes a wired stub — Twine/Yarn/Ink consensus).       3. Fact lifting: select-to-lift. Select a passage in the document text → 'lift as fact' → fact born with quote + source pre-filled, focus in the label field. Auto-suggested lifting (LLM/heuristic) is explicitly out of scope for this map.

      4. Script surface = the raw markup 0.2 text, live-compiled (SB-025's proven form). No WYSIWYG document mode until a probe shows markup prose is the friction.

The question: SB-036's probe says authoring is linear and fluid — write a document, see what facts it lifts, wire each fact to the dialog it triggers, loop back. The canvas as built is graph-first and static. What is the editor's primary authoring loop, and what does that do to DD-003 (canvas primary, markup the store)? Options run from (a) canvas stays primary but gains a document-first creation flow, through (b) a hybrid where a linear/script surface authors and the canvas structures and navigates, to (c) demote the canvas to a map you read, not write.

Why it blocks: every further editor investment — weave surfacing (SB-037) included — depends on which loop we build for.
